# TypeScript 小范围改动流程

## 适用场景

- 修改已有 TypeScript 函数、接口或配置解析逻辑。
- 修复能够稳定复现的缺陷。
- 在不改变整体架构的前提下补充一项小功能。
- 不适用于从零搭建项目或跨多个服务的大规模重构。

## 开始前确认

- 查看仓库中的 `package.json`、测试命令和 TypeScript 配置。
- 查看工作区状态，避免覆盖尚未提交的修改。
- 找到当前行为对应的实现和已有测试，确认改动边界。

## 操作步骤

1. 用最小输入复现当前问题，记录实际结果和预期结果。
2. 在最接近现有测试的位置增加一个失败用例，确保它因目标行为尚未实现而失败。
3. 只修改解决该问题所需的代码，不顺带整理无关模块。
4. 先运行新增测试，再运行受影响模块的完整测试。
5. 执行 TypeScript 类型检查，处理新增的类型错误。
6. 查看最终差异，确认没有生成文件、凭据和调试输出混入改动。

## 检查方法

- 运行项目定义的单元测试命令，新用例和原有用例均应通过。
- 运行 `tsc --noEmit` 或项目已有的类型检查脚本。
- 用最初的复现输入再次验证，结果应与预期一致。
- 查看 `git diff --check`，不应出现冲突标记或意外空白问题。

## 常见问题

- 测试一开始就通过：测试没有覆盖缺失行为，应重新检查断言和调用路径。
- 修改范围不断扩大：先暂停并重新确认根因，不要用重构掩盖问题。
- 只修复类型报错：类型错误可能只是表面现象，应确认运行时行为也得到验证。
- 工作区已有修改：保留原修改，只处理与当前任务直接相关的文件。

## 完成标准

- 问题可以由自动化测试复现并验证修复。
- 类型检查及相关测试通过。
- 改动中没有无关文件和临时调试代码。
