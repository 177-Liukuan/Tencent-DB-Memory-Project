## 任务一的整体定位

“Proxy 系统提示词注入优化”的核心目标是：

> 在尽量减少注入 Token 的同时，让模型在确实需要 Memory、Skill 或 Knowledge 时调用正确工具，在普通编码任务中不误调用，并保持 Prompt Cache 的稳定性。

这里优化的不是“记忆内容本身好不好”，而是一个更原子的能力：

> Proxy 注入的工具描述，能否让模型在正确时机识别并调用正确工具。

会议转写里的“Scale”“Cloud Code”等词，结合正式题目应分别理解为 **Skill**、**Claude Code**；正式题目文件的术语优先级更高。

------

## 一、正式题目内容

### 1. 当前问题

TDAI Memory 的 Proxy 会向 Agent 的系统提示词注入多类内容：

| 注入块                  | 主要内容                               |
| ----------------------- | -------------------------------------- |
| `<tdai_memory_tools>`   | 6 个 Memory 工具的 curl 调用模板和约束 |
| `<memory-tools-guide>`  | 什么情况下应该或不应该查询记忆         |
| `<tdai_profile_memory>` | L3 用户画像、L2 场景索引               |
| `<skill_tools>`         | 4～10 个 Skill 工具的 curl 模板        |
| `<available_skills>`    | 当前 Agent 可使用的 Skill 列表         |
| `<knowledge_tools>`     | Knowledge 工具描述                     |

当前主要问题包括：

- 多个区块之间存在重复描述和重复约束；
- curl 模板、参数、错误码和示例过长；
- 随着 Memory、Skill 等资产增加，注入内容继续膨胀；
- 上下文过长不仅增加成本，还可能削弱模型对关键指令的关注；
- 如果压缩过度，又可能导致工具调用率下降。

### 2. 需要优化的指标

正式题目要求同时考虑四项指标：

- **有效调用率提高**：该调用时能够调用；
- **误调用率降低**：普通任务中不乱调用；
- **工具选择正确率提高**：需要调用时选对 Memory、Skill 或 Knowledge 工具；
- **注入 Token 数降低**：减少系统提示词及工具描述的上下文占用。

同时还有一个容易被忽略的约束：

- 不应因为动态注入内容的位置或顺序不断变化，而破坏模型的 **Prompt Cache / 前缀缓存命中率**。

### 3. 官方建议的优化方向

题目给出的方向主要包括：

- 合并不同注入块中的重复说明；
- 缩短工具字段描述；
- 删除重复示例；
- 压缩错误码及操作细节；
- 对比“多个独立区块”和“统一工具区块”；
- 强化“什么时候调用”的触发条件；
- 弱化模型不需要理解的执行细节；
- 调整 `system.before_tools`、`system.suffix` 等注入位置；
- 在不同模型上比较压缩效果。

相关代码主要位于：

- `MemoryProxy/src/injection/index.ts`
- `MemoryProxy/src/injection/pipeline.ts`
- `tdai-tools-injector.ts`
- `tdai-profile-memory-injector.ts`
- `skill-tools-injector.ts`
- `skill-injector.ts`
- `knowledge-tools-injector.ts`

题目建议优先修改各注入器内部的 `render*Block` 纯函数，尽量避免大范围破坏现有注入管线。

### 4. 正式交付物

任务一要求的主要成果是：

1. 优化前后的实验报告；
2. 有效调用率、误调用率、工具选择正确率等对比；
3. Token 节省量；
4. 优化方案说明；
5. 对应代码 PR。

## 二、导师对任务一的解读

导师实际上把任务一拆成了两条可选路线。

| 路线                                 | 核心工作                                       | 主要评价依据                          |
| ------------------------------------ | ---------------------------------------------- | ------------------------------------- |
| 路线 A：提示词压缩与评测             | 构造数据集、跑基线、压缩注入内容、重新评测     | Token 降低且调用效果不下降            |
| 路线 B：Fake Tool 攓造成 Native Tool | 将 curl/命令式伪工具改成模型原生结构化工具调用 | Proxy 工具执行闭环及 Agent 适配完整性 |

这两条路线是导师给出的实践建议，不是必须同时完成的硬性要求。导师明确表示，只要能给项目带来实际价值，方案可以自行调整。

## 三、路线 A：提示词压缩与评测

### 1. 导师建议的实验流程

比较完整的流程是：

1. 先生成或准备 Memory、Skill 等资产；
2. 在 Panel 中确认这些资产确实存在且可检索；
3. 构造需要调用工具才能正确处理的测试任务；
4. 使用当前最新版本跑 Baseline；
5. 记录工具调用率和调用正确性；
6. 压缩、合并或重新组织提示词；
7. 在相同模型、相同数据集上重新测试；
8. 比较调用效果、Token、延迟和缓存稳定性。

导师提到过将原本约 10K 的注入内容压缩到约 3K～4K，属于一种示例性的优化幅度，并不是正式题目规定的硬性 KPI。

### 2. 数据集应当包含什么

导师强调，数据集不是泛化的代码能力测试，而是“模型应不应该调用某个工具”的测试。

建议包含：

- **正例**：任务必须查询某条 Memory 或某项 Skill 才能正确处理；
- **工具选择例**：需要调用工具，但不同任务应调用不同工具；
- **负例**：纯编码或无关任务，不应调用 Memory/Skill/Knowledge；
- **混淆例**：任务表面涉及历史信息，但当前上下文已经足够，不应重复查询；
- **生成与召回场景**：既覆盖资产如何准备，也覆盖后续如何被正确检索。

开源数据集可以使用，但必须根据项目工具和资产结构进行改造，不能直接拿通用数据集评测。

### 3. 评测边界

导师特别强调：

> 只评价模型是否在正确时机调用了正确工具，不评价工具返回的 Memory 或 Skill 最终是否真正提升了整个编码任务的完成质量。

例如，预期调用 `memory_search`：

- 没调用：失败；
- 调用了 `skill_search`：失败；
- 在不需要工具的普通任务中调用了 Memory：误调用；
- 调用了正确工具，但返回内容对最终任务帮助有限：在本任务的原子评测中仍可算“调用正确”。

## 四、路线 B：Fake Tool 改造成 Native Tool

### 1. Fake Tool 是什么

当前方案把工具调用方式写进系统提示词，让模型通过已有的 Bash/curl 能力访问 TDAI Memory 服务。

它本质上是：

> 用提示词把 HTTP 请求包装成“看起来像工具”的调用方式。

缺点是：

- curl 模板占用大量 Token；
- 模型要理解 URL、参数和命令格式；
- 容易输出错误命令；
- 不同工具的模板和约束会重复。

### 2. Native Tool 是什么

Native Tool 是把 Memory、Skill 等能力直接以模型协议支持的结构化工具定义加入 `tools` 列表。

理想流程是：

1. Agent 请求到达 Proxy；
2. Proxy 向请求的 `tools` 数组追加 TDAI 工具 Schema；
3. 模型返回结构化 `tool_call`；
4. Proxy 判断该工具归谁执行；
5. TDAI 工具由 Proxy 拦截和执行；
6. 执行结果重新送回模型；
7. Agent 客户端自己的工具仍原样转发给客户端执行。

这样模型不需要在系统提示词里阅读大量 curl 模板，能够依赖其原生 Tool Calling 能力。

### 3. 真正困难的地方

导师认为这会是一个较大的 PR，因为项目需要支持 Claude Code、Codex、WorkBuddy 等多个 Agent，而不同 Agent 可能使用 OpenAI、Anthropic 或其他协议格式。

需要处理：

- 不同协议的工具定义格式；
- 不同协议的 `tool_call` 和 `tool_result` 格式；
- 流式与非流式响应；
- Proxy 工具与客户端工具的路由；
- 一个响应中同时出现多个工具调用；
- Proxy 工具与客户端工具混合并行调用；
- Proxy 执行完成后，如何把结果重新送回模型继续推理；
- 客户端不知道 Proxy 拦截了哪些工具调用时，如何保持对话状态一致。

### 4. 导师所说的“数据库”

导师这里的“数据库”主要不是指长期 Memory 数据库，而是 Proxy 侧维护的隐藏会话状态。

由于某个 TDAI 工具调用被 Proxy 拦截并执行，客户端可能完全看不到：

- 模型生成过这个 `tool_call`；
- Proxy 返回过对应 `tool_result`；
- 模型为什么继续生成后续回复。

因此 Proxy 需要保存这些客户端不可见的调用记录，并在下一次模型请求时重新注入，形成完整的模型对话历史。数据库在这里相当于一个：

> Proxy 侧的隐藏工具调用账本或影子对话记录。

这个机制在“同一轮既调用客户端 Bash，又调用 Proxy 的 Memory 工具”的混合并行场景中尤其重要。

## 五、导师给出的具体建议

### 1. 先把方案想清楚再开发

初步方案至少要说明：

- 选择哪条路线；
- 数据如何构造；
- 基线如何建立；
- 准备用什么指标；
- 从哪些注入块或协议开始改；
- 最小可验证闭环是什么。

导师希望先对齐方案，避免写完较大改动后才发现方向不一致。

### 2. Baseline 尽量使用最新版本

建议以项目最新版本或最新 Tag 作为基线，这样结果更有参考价值。如果优化代码基于其他合理版本，也需要记录清楚版本和差异。

### 3. 前后对比必须控制变量

最重要的是：

- 同一模型；
- 同一数据集；
- 相同模型参数；
- 相同资产；
- 相同测试环境。

没有必要一开始就测试大量昂贵模型。可以先用 DeepSeek、MiniMax 等成本较低的模型完成方案筛选，再选一个代表性模型验证。多模型测试是加分项，不是硬性要求。

### 4. 避免 Claude Code 自身记忆污染实验

重复测试时，不应一直复用同一个 Claude Code 实例或项目目录。因为客户端自身可能积累上下文或记忆，第二次运行表现更好不一定是 Proxy 优化造成的。

导师建议每次实验使用新的目录或隔离环境。

### 5. 使用 Langfuse 观察链路

可以通过 Langfuse 检查：

- Proxy 实际注入了什么；
- 最终请求 Token 数；
- 模型是否生成工具调用；
- 调用了哪个工具；
- 调用耗时；
- 一次任务经过多少次模型请求。

它适合用于定位“压缩后为什么调用率下降”以及 Native Tool 的执行链是否完整。

### 6. Native Tool 路线以工程闭环为主

导师明确指出，选择 Native Tool 路线后，不必完成与提示词压缩路线同等规模的评测。主要工作可以放在：

- Agent 请求适配；
- Tool Schema 注入；
- 工具调用识别；
- Proxy 工具执行；
- 客户端工具透传；
- 结果回填和模型再次推理；
- 多协议或多 Agent 扩展。

如果时间有限，先完整适配 Claude Code 一个 Agent，只要方案闭环且具有项目价值，也可以接受；Fake Tool 与 Native Tool 的简单对比实验属于加分项。

## 六、综合三份文档后的任务边界

最重要的几个边界是：

1. **正式题目的主线是提示词注入优化和量化评测。**
2. **Native Tool 是导师提出的工程型替代路线，不是所有参与者都必须完成。**
3. **不能只追求 Token 降低，必须证明工具调用能力没有明显退化。**
4. **任务一评测的是工具调用行为，不是 Memory 内容质量或最终代码质量。**
5. **Token 应使用真实 tokenizer 或接口统计，不能简单把“2 万字符”当成“2 万 Token”。**
6. **Native Tool 的关键不是把 Schema 塞进请求，而是完成执行、回填、重入和状态一致性的闭环。**
7. **导师总体倾向于简单、有效、稳定、能合入项目的方案，而不是为了技术复杂度做过度设计。**

结合你目前关注的 Native Tool 方向，比较合理的课题表述可以是：

> 在保持现有 Proxy 注入框架的基础上，将 Memory/Skill 的 curl 式 Fake Tool 逐步改造成模型原生 Tool Calling，并实现 Proxy 工具和客户端工具的统一识别、分流执行、结果回填及隐藏会话状态管理；优先完成单一 Agent 的完整闭环，再扩展到多协议、多 Agent，并通过小规模 Fake/Native 对比验证 Token 与调用稳定性的变化。
