# 项目协作与代码开发规范

> 适用仓库：TencentDB Agent Memory baseline（审阅基线：`v2.0.1-beta.2`）
>
> 原则：尊重并延续现有项目风格；本文件中的“建议规范”表示代码库尚无统一实践，实施时应优先与维护者确认。

## 1. 基本原则

1. 修改应落在职责所属模块内，不因单个需求顺带重构无关代码。
2. 优先复用已有接口、工厂、Adapter、Registry、Store/Repo 和响应封装，不另建平行体系。
3. 对外兼容优先：既有路径、Header、字段名、错误码、默认值和配置别名不得无迁移方案地改变。
4. 数据面、管理面、可观测性和可选扩展保持解耦；辅助能力失败不得无依据地拖垮主链路。
5. 凭据、真实配置、运行数据、日志、依赖目录和构建产物不得提交。

## 2. 仓库与模块边界

| 目录 | 主要职责 | 现有组织方式 |
|---|---|---|
| `MemoryCore/` | Memory Gateway、四层记忆管线、Skill、Metadata、Offload | `core/` 放领域逻辑，`gateway/`/`metadata/router/` 放 HTTP 边界，`adapters/` 适配宿主，`store/`/`storage/` 隔离持久化 |
| `MemoryProxy/` | 多 Agent、多协议 LLM Proxy、身份/会话、注入与回流 | Handler 编排主流程；`agent-adapters/`、`injection/adapters/` 处理客户端和协议差异；`routes/`、`storage/`、`db/`、`skill/`、`memory/` 分域组织 |
| `MemoryKnowledge/` | Wiki、Code Graph、MCP/HTTP 查询 | `routes/` 保持薄层，`engines/` 放算法，`store/` 放状态，`source-fetcher/` 以 Registry 扩展来源 |
| `MemoryPanel/` | Stateless Control 后端与 React 管理面 | 后端采用 domain / kernel ports / adapters / HTTP routes；前端按 page + components + hook + service 组织 |
| `sdk/memory-core/` | TypeScript、Python SDK | 传输层、错误类型、版本客户端分离；公开 API 由入口文件统一导出 |
| `deploy/` | 镜像构建、发布和本地部署 | 脚本先校验参数/敏感信息，再准备 context、构建和验证 |

- 新代码应放在最窄的业务目录内；仅被一个功能使用的类型、辅助函数与该功能同目录。
- 跨功能稳定契约才进入 `types.ts`、`interface.ts`、`ports/` 或模块入口 `index.ts`。
- `index.ts` 主要用于公开导出、注册或装配，不堆放具体业务算法。
- 协议差异放 Adapter，存储差异放 Store/Repo/Backend，实例选择放 Factory/Resolver；业务层依赖接口，不直接依赖具体实现。
- 生成文件、`dist/`、`node_modules/`、coverage、数据库与运行目录不作为源码修改对象。

## 3. Git 分支、Commit 与 PR

### 3.1 分支与目标分支

- 当前历史中存在 `main`、`feat/server*`、发布同步分支；`CONTRIBUTING*` 仍提到 `master`、`develop_*`，而当前 PR CI 监听 `main`。因此**发起 PR 前必须以远端当前默认分支和维护者指示为准，不得仅按旧文档猜测目标分支**。
- 已有命名示例为 `fix/<topic>`、`feat/<topic>`。新分支使用小写、短横线和明确主题，例如 `feat/native-proxy-tools`、`fix/tool-timeout`。
- 发布版本由维护者通过 release commit/tag 处理；普通功能分支不得自行移动 `latest`、`beta` 或发布 tag。

### 3.2 Commit

遵循仓库 `CONTRIBUTING*` 中的 Conventional Commits 与 DCO：

```text
<type>(<scope>): <subject>

<body>

Signed-off-by: Name <email>
```

- `type` 使用 `feat`、`fix`、`perf`、`refactor`、`docs`、`test`、`chore`、`style`、`revert`。
- `scope` 优先使用现有模块/子系统：`memory-core`、`proxy`、`panel`、`knowledge`、`sdk-ts`、`sdk-py`、`deploy`、`docs`；更精确且稳定时可用 `gateway`、`skill`、`offload` 等历史 scope。
- 使用 `git commit -s` 生成 `Signed-off-by`。历史早期提交并非全部签名，但现行贡献文档已明确要求 DCO，不得沿用早期例外。
- subject 简洁描述结果；body 说明动机、兼容性、关键取舍和验证。关联问题使用 `Fixes/Closes #...`；保留必要的 `Co-authored-by`。
- 每个 Commit 只包含一个可独立解释和验证的逻辑变更。大规模 release/sync commit 是发布流程产物，不是日常开发粒度范例。
- 不提交 `.env`、真实 YAML/JSON 凭据、数据库、日志、打包文件或临时诊断产物。

### 3.3 PR

按 `.github/PULL_REQUEST_TEMPLATE.md` 至少填写：

- 做了什么、为什么做；
- 关联 Issue；
- 变更类型；
- 本地验证命令与结果；
- 对既有功能、配置、协议和部署的影响。

涉及接口、配置、存储或多 Agent 协议时，补充兼容/回滚说明。PR 应通过目标模块检查和仓库 CI；触及 Skill 队列时还必须运行 `MemoryCore/scripts/ci/check-skill-queue-isolation.sh`，不得常规使用跳过开关。

## 4. 命名与代码风格

### 4.1 TypeScript / React

- 主要 TypeScript 模块采用 ESM；已有 `tsconfig.json` 的服务/SDK 启用严格类型检查。代码延续 2 空格缩进和分号。
- `MemoryCore`、`MemoryProxy`、`MemoryKnowledge`、TypeScript SDK 使用双引号；`MemoryPanel` 后端和 Web 使用单引号。修改文件时遵循该模块现状，不跨模块统一引号。
- Node 端相对导入通常写编译后扩展名 `.js`，例如 `./types.js`；前端 Vite 代码延续当前无扩展名/`@/` alias 风格。
- 文件名：Node 后端以 `kebab-case.ts` 为主；React 组件用 `PascalCase.tsx`；Hook 用 `useXxx.ts`/`useXxx.tsx`；样式文件跟随组件现有命名。
- 变量/函数用 `camelCase`，类/接口/类型用 `PascalCase`，常量用 `UPPER_SNAKE_CASE` 或现有 `as const` 对象。
- 优先 `unknown` + 边界收窄，避免新增无约束 `any`。确需 `any` 时限定在第三方/动态模块边界并解释原因。
- 类型导入使用 `import type`。公开接口写必要 JSDoc；注释解释“为什么、约束和兼容背景”，不复述代码。
- 前端提交前使用既有 ESLint/Prettier；当前格式为单引号、尾逗号、100 列、2 空格、LF。

### 4.2 Python 与 Shell

- Python 遵循 PEP 8、`snake_case`、类型注解和模块/公开对象 docstring；同步与异步客户端保持行为对称。
- Shell 新脚本沿用 `#!/usr/bin/env bash` 和 `set -euo pipefail`，显式校验参数与依赖；变量加引号，错误输出到 stderr，临时文件设置清理 trap。

## 5. 接口与数据结构

### 5.1 HTTP/API

- 对外 JSON 字段延续 `snake_case`，内部 TypeScript 对象延续 `camelCase`；转换集中在 HTTP/SDK 边界，不在领域层混用。已有协议例外保持兼容，不借新功能全局改名。
- v2/v3 与 Knowledge API 的通用响应形态为：

```json
{
  "code": 0,
  "message": "ok",
  "request_id": "...",
  "data": {}
}
```

- 成功通常 `code === 0`；错误使用稳定业务码或 HTTP 语义码。`data` 是省略还是 `null` 必须跟随目标子系统现有 envelope，不自行创造第三种形态。
- 新数据面能力优先进入当前主推的 `/v3` 契约；仅为兼容既有客户端时扩展 v2，并明确兼容期限。
- 租户/身份继续使用既有 Header（如 `x-tdai-service-id`、`x-tdai-user-key`）和 IdFields；不得允许模型或不可信 body 覆盖由认证/session 推导的身份。
- 外部输入在边界校验。已有模块优先使用 Zod/JSON Schema；文件路径和 ID 使用白名单、长度限制并阻止绝对路径与路径穿越。
- 时间存储使用 UTC ISO 8601；面向用户/LLM 的时区转换使用现有时间工具，不散落自行格式化。
- 列表接口延续已有 `items`/`messages`、`total`、`limit`/`offset` 或既定 cursor 语义，不混搭新的分页模型。

### 5.2 Tool 契约

- 工具名使用稳定的 `snake_case`，定义包含 `name`、可操作的 `description` 和 JSON Schema；必填字段、枚举、范围、默认值与限制必须写入 schema/description。
- 工具定义、协议序列化、身份注入和真实执行应分层。OpenAI/Anthropic/Agent 差异进入 Adapter，不复制业务实现。
- 工具错误应可被调用方或模型识别：使用现有 envelope，或像 `MemoryCore/src/core/skill/skill-tools.ts` 一样返回稳定的 JSON 错误对象；不得把原始异常栈、上游响应体或凭据暴露给模型。
- 写工具必须执行权限校验；已有版本化资源继续使用 `expected_version` 乐观锁。读/写身份字段分开构造，审计字段不得误入检索条件。
- 控制面操作和破坏性操作默认不作为模型工具暴露；确需开放时必须有明确授权、幂等/冲突语义与审计。

## 6. 配置与环境变量

- 配置入口集中管理：类型/默认值、文件解析、CLI/env 覆盖和运行时归一化不得散落在业务代码。
- 延续各模块现有优先级：例如 Proxy 为 `CLI > YAML > DEFAULT_CONFIG`；新增来源时必须在代码和文档中明确优先级。
- 配置文件字段延续本模块 `camelCase`；环境变量使用 `UPPER_SNAKE_CASE` 并保留模块前缀（如 `TDAI_`、`KNOWLEDGE_`、`PROXY_`、`VITE_`）。
- 每个新配置项同时完成：类型、默认值、解析/校验、示例配置、README 说明；废弃项保留兼容别名时写明优先级和迁移路径。
- 兼容性敏感或内部实验能力使用 feature flag；默认值应保持旧行为。生产危险的 debug/bypass 开关必须默认关闭并在日志中可识别。
- API key、token、密码和真实实例配置只通过运行环境/Secret 或 gitignored 本地文件注入；示例只放空值、`REPLACE_ME` 或明确假值。
- 启动日志可记录开关、端点、backend 和降级状态，但不得打印凭据。新增部署配置还需同步 Docker/启动脚本和 secret scan 范围。

## 7. 日志、异常与降级

- 优先使用目标模块已有 Logger 门面/接口，不在业务代码新增独立日志体系。Proxy 的结构化事件名延续 `domain.action`/`domain.action.state`，字段使用稳定 ID、状态、耗时和计数。
- 请求链路携带 `request_id`/`trace_id`；日志记录关联 ID、路由、耗时、结果码和必要维度，避免记录完整 prompt、消息、工具结果和请求/响应体。
- 对异常统一按 `err instanceof Error ? err.message : String(err)` 收窄，并在对外返回前分类与脱敏。未知 5xx 对客户端只返回通用消息和关联 ID，详细堆栈仅进入服务端安全日志。
- 使用现有 `sanitize`/`sanitizeObject` 或同等集中脱敏逻辑；严禁记录 Authorization、API key、临时密钥、密码和完整用户内容。
- 仅可观测性、缓存预热、遥测、异步回流等明确 best-effort 场景可吞异常；catch 处必须用注释或日志说明不阻塞主链路的原因。
- 降级必须符合一致性语义并可观测。多节点共享状态不得静默降到进程本地存储；不可安全降级时应启动失败或返回 degraded/503。
- 超时、重试和并发上限必须显式、可配置或使用模块既有默认；仅重试瞬时错误，4xx/校验/权限错误不盲目重试。

## 8. 测试与验证

仓库贡献要求是“新功能补测试，Bug 修复优先补回归测试”。历史测试实践为 Vitest + pytest，常用依赖注入、fake/mock、纯函数边界测试、错误/兼容/安全用例和少量 E2E/Smoke。

当前发布基线未跟踪会被 Vitest/pytest 默认发现的单元测试文件，直接运行四个 Node 服务的 `npm test` 会因 `No test files found` 退出 1；这属于 baseline 快照缺口，**不得视为新增功能可以不写测试**。

| 修改范围 | 至少运行 |
|---|---|
| `MemoryCore` | `npm test`、`npm run build`；Skill 相关再跑 `npm run lint:skill-isolation`，按功能补相应 smoke/E2E |
| `MemoryProxy` | `npm test`、`npm run typecheck`；涉及协议时分别验证 OpenAI/Anthropic/Responses 路径 |
| `MemoryKnowledge` | `pnpm test`、`pnpm typecheck`、`pnpm build`；接口/容器改动补 smoke |
| `MemoryPanel` 后端 | `npm test`（或 pnpm 等价命令）、`npm run typecheck`、`npm run build`；相关授权链路跑现有 E2E 脚本 |
| `MemoryPanel/web` | `npm run lint:check`、`npm run format:check`、`npm run build` |
| TypeScript SDK | `npm test`、`npm run build` |
| Python SDK/插件 | `pytest`；构建发布包时再验证 wheel/build |

- 测试文件必须匹配各模块 Vitest 配置：Core 可用 `src/**/*.test.ts`；Proxy 使用 `src/**/__tests__/**/*.test.ts`；Panel 后端使用 `tests/**/*.test.ts`；SDK 使用 `tests/**/*.test.ts`。
- 单元测试不得依赖真实云凭据或外网；网络、时钟、存储、LLM 和进程生命周期通过依赖注入/fake/mock 控制。
- E2E/Smoke 若需要真实服务，必须由显式环境变量启用，先做前置检查，并保证测试数据/实例可清理。
- PR 中列出实际执行的命令和结果；无法执行的检查要说明原因与替代证据，不能写笼统的“已测试”。

## 9. 文档与依赖管理

### 9.1 文档

- 用户可见能力、配置、安装方式或接口变化，应同步目标模块 README；仓库长期采用中英文成对文档，已有双语页面应同步更新。
- 公共 API 变化同步 OpenAPI、TypeScript/Python SDK、SDK README/Agent Guide；行为变化同步 `CHANGELOG.md`。
- 配置示例必须可复制，示例凭据必须是假值；命令、默认值、端口、路径和字段要与代码一致。
- 重要设计取舍可写 design/architecture 文档；提交前确认引用文件实际被 Git 跟踪，避免新增当前仓库中已有的悬空 `docs/...` 引用。
- 带有 `Generated by ... / Do not edit manually` 标记的文件必须通过生成器更新；若当前发布快照缺少生成源，先与维护者恢复/确认权威契约，不直接手改生成结果。
- 注释、README 和 OpenAPI 不重复维护互相矛盾的默认值；代码默认值为最终事实，文档变更需与其同一 PR 提交。

### 9.2 依赖

- 依赖只加入实际使用它的模块 `package.json`/`pyproject.toml`，优先平台原生能力和仓库已有库。
- 保持现有运行基线：服务端 Node.js 22（Core 至少 22.16），TypeScript SDK Node.js 18+，Python 3.9+；不得无说明抬高版本。
- Core/Proxy/容器文档主要使用 npm；Knowledge 本地文档使用 `pnpm --ignore-workspace`；Panel 同时保留 npm/pnpm 工作流。修改依赖时按目标模块文档执行，并更新该模块所有已跟踪 lockfile，避免只更新其中一份。
- 原生、私有或重量依赖继续采用现有 optional dependency / dynamic import / adapter 模式，并定义缺失时的明确行为。
- 不手改 lockfile 和生成代码；使用包管理器/生成脚本。不得提交 `node_modules`、SDK `dist`、tarball、wheel。

## 10. Native Tool 开发约束

以下用于后续 Native Proxy Tool 的真实工具调用实现。

### 必须延续的现有模式

1. 先定义协议无关工具契约，再由 OpenAI/Anthropic/Responses Adapter 转换线格式；不得在每个 Handler 各写一套业务逻辑。
2. 工具 schema 和执行实现均使用同一稳定工具名；参数经 JSON Schema/Zod 校验后才能进入执行层。
3. 身份由已认证请求和 Session 上下文注入，模型参数中不接受 `user_id`、`team_id`、`agent_id` 等越权覆盖。
4. 对 Core/Knowledge/外部服务的调用通过既有 Client/Bridge/Port，统一处理 endpoint、Header、timeout、envelope 和错误映射。
5. 只读与写入工具分组；写工具受 feature flag、权限、版本冲突和审计约束。默认不暴露删除/销毁类工具。
6. 注册和装配集中在 Registry/Factory/入口，单个工具文件不读取全局配置、不自行创建单例。
7. 工具结果设置大小/条数上限并可截断；日志只记工具名、调用 ID、状态、耗时、结果大小，不记完整参数和结果。


### 建议规范：最小测试集

- schema：必填、类型、枚举、上下限、未知字段策略；
- registry：重复名称、未知工具、启停开关和顺序；
- execution：成功、业务错误、上游 4xx/5xx、timeout/abort、异常脱敏；
- auth：身份只来自可信上下文，跨 tenant/agent 访问被拒绝；
- protocol：OpenAI、Anthropic、Responses 的定义与 tool result 往返不丢字段；
- safety：只读/写权限、结果大小上限、幂等或乐观锁、日志无敏感信息；
- regression：现有非 tool 请求、静态 curl tool 注入和各 Agent 路由保持原行为。

## 11. 完成定义（DoD）

提交前逐项确认：

- [ ] 变更位于正确模块，复用了现有接口/Adapter/Factory/Store 模式；
- [ ] 外部字段、Header、错误码、默认值和兼容别名未被意外改变；
- [ ] 新配置已补类型、默认值、校验、示例和文档，敏感值未入库/日志；
- [ ] 新功能有正常、边界、错误和安全测试；Bug 有回归测试；
- [ ] 已运行目标模块 typecheck/build/test 及必要 E2E/Smoke，并记录结果；
- [ ] README/OpenAPI/SDK/CHANGELOG 已按影响同步；
- [ ] Commit 使用 Conventional Commits 与 DCO，PR 填写完整并指向维护者确认的目标分支；
- [ ] `git diff` 中没有无关格式化、生成产物、真实配置、数据库、日志或临时文件。
